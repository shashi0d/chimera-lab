# R8. Generative evolution: how to run an evolution loop with models

Doc: docs/evolution/research/R8_generative_evolution.md
Status: research, first pass (Oct 31, 2026)
Feeds: ALGORITHM.md (genome format, variation, selection, archive, user loop)
Related: R1 to R6 (the rules that score and constrain each candidate), R7 (design taste)

## Why this doc exists

R1 to R6 say what a good fusion looks like. This doc covers the machinery: how to represent a creature so it can be varied, how to make offspring with a language model, how to pick survivors without collapsing to one look, and how to keep a human in the loop without tiring them out. It draws on artificial life, evolutionary computation and recent work that uses large models inside evolutionary loops.

Tag vocabulary for rule cards: size, body, head, face, ears, mane, tail, limbs, feet, coat_pattern, coat_color, coat_texture, skull, behavior, all_traits, pipeline.

## Key takeaways for the engine

1. Keep a genome separate from the picture. Evolve a structured text plan (the genotype); the image is a rendering of it (the phenotype). Every edit changes the plan, then the image is re-rendered.
2. A language model can act as the crossover and mutation operator for text genomes, including text-to-image prompts.
3. Do not keep only the single best result. A quality-diversity archive keeps the best creature for each combination of a few meaningful axes, which gives users real choices and often finds a better overall result.
4. Models can also judge quality and diversity of subjective outputs, with reasonable agreement with people, but this needs human spot checks.
5. People tire fast in interactive evolution. Short sessions, branching from saved creatures and a constrained search space reduce fatigue.

## 1. Genome and phenotype: Sims' virtual creatures

Karl Sims evolved virtual creatures whose bodies and nervous systems were both generated by genetic algorithms. The genotype was a directed graph of nodes and connections that acted as developmental instructions; growing it produced the phenotype, a hierarchy of 3D parts, and repeated or recursive parts came from reusing graph nodes. Fitness could be computed automatically or supplied interactively by a person [S1].

Engine mapping: our genome is the trait plan (per trait: donor, operator from R1, strength, region) plus host, habitat and mode. It is the thing that gets mutated, crossed, stored and cited. The image model only renders it. This also gives us lineage and explainability: every creature can show the plan it grew from.

## 2. Language models as variation operators

Meyerson and colleagues showed that prompting a language model with a few parent genomes and parsing its output as offspring works as an intelligent crossover operator, which they call language model crossover. They demonstrated it on bit strings, equations, sentences, Python code and text-to-image prompts, and concluded it is a flexible way to evolve anything representable as text [S2].

Engine mapping: crossover of two creature plans, or mutation of one, can be a Muse Spark call that receives the parent plans plus the rule cards and returns a new plan in the same schema. Because the plan is text with a fixed schema, offspring can be validated by code before any image is rendered. That specific use of Muse Spark is our design, not something the paper tested.

## 3. Keep a map of diverse elites, not one winner

Mouret and Clune's MAP-Elites divides the space of solutions along a few dimensions chosen by the user, then keeps the best solution found in each cell. New candidates come from mutating elites and are placed in the cell their features fall into. The result is a large set of high-performing but qualitatively different solutions, and because it explores more widely it also tends to find a better single solution than standard search [S3]. Follow-up work describes the family of such methods as quality-diversity search [S4].

Engine mapping: the archive axes should be things a user cares about. A natural choice for Chimera Lab is identity balance (how much the creature reads as parent A versus parent B) crossed with habitat or mode (hybrid, chimera, mythic). The grid itself is a good interface: the user sees a spread of distinct, good options instead of one result. The specific axes are our design and are UNVERIFIED until tested.

## 4. Models as judges of quality and diversity

Quality-Diversity through AI Feedback (QDAIF) uses language models both to generate variation and to evaluate the quality and diversity of candidates in subjective domains such as stories and poetry. It covered more of the target space with high-quality samples than non-QD baselines, and human evaluation showed reasonable agreement between AI and human judgments [S5].

Engine mapping: the readability critic from R6 and the rule-card checks become the quality score; a model rating of identity balance (or habitat) places each creature in its archive cell. R6 warns that vision models can lean on texture, so the critic's scores need a silhouette check and occasional human review.

## 5. Keeping a human in the loop

In interactive evolutionary computation the fitness function is replaced by a person choosing which candidates breed. A widely reported problem is user fatigue: people evaluate only a few generations before tiring [S6]. Picbreeder, a large online experiment from the University of Central Florida, let users evolve images and, most importantly, continue evolving other users' images; its authors report that this branching helps collaborative evolution overcome user fatigue [S7]. Bontrager and colleagues evolved images inside the latent space of a generative model restricted to one class of image, hypothesizing that a narrower space needs fewer generations from the user [S6].

Engine mapping:
- Keep interactive sessions short: a few rounds, each showing a small grid.
- Every saved creature stores its parents, so anyone can branch from it later.
- Constrain the space: all candidates share the creature-plan schema and pass R3 checks before the user sees them, so the user never wastes a choice on a broken body. The fatigue benefit of a constrained space is a hypothesis in the source, so that card is UNVERIFIED.

## 6. Suggested loop (design, to be tested)

1. Seed: build an initial plan from R2 (if a real hybrid exists) or R5 (chimera path), with R1 operators per trait.
2. Vary: language model crossover and mutation produce a small batch of new plans.
3. Validate: code checks schema and hard rule cards; R3 checks run; failures are repaired or dropped.
4. Render: the image model draws each surviving plan.
5. Judge: readability critic, silhouette check against the planned host (R6), visible habitat trait (R4).
6. Archive: place each creature in its cell; keep the best per cell.
7. Show: the user sees a few elites from different cells, picks, edits a gene, or branches.

Hard rule cards act as filters. Soft cards act as score penalties, so the models stay creative and the rules stay guardrails, which matches the project's stated approach.

## What this doc does not settle

- How many rounds and how large a batch the Meta API budget supports. That needs a cost test.
- Whether Muse Spark is a reliable crossover operator for our schema. That needs a small live test.
- Which archive axes users find most useful.
